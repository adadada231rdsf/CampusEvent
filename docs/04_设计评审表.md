## 2. 评审要点（请评审同学逐项确认）

| # | 评审项 | 关注点 | 结论（通过/需修改） | 意见 |
| --- | --- | --- | --- | --- |
| 1 | 需求完整性 | P2-F01~F08 是否都有对应的类/用例，有无遗漏 |  |  |
| 2 | 职责划分 | 实体、Service、策略、通道、仓储的职责是否单一、有无越界 |  |  |
| 3 | 策略模式 | 抽象接口是否只暴露必要方法；新增报名方式是否无需改 Service |  |  |
| 4 | 名额检查归属 | 为什么放在策略基类而非各策略；批准复查是否复用同一规则 |  |  |
| 5 | 观察者模式 | 通知通道接口是否与业务解耦；新增渠道是否需要改域层 |  |  |
| 6 | 事务边界 | 通知失败是否会影响报名；补偿与留痕是否充分 |  |  |
| 7 | 幂等与重复通知 | 去重键是否合理，重试是否会产生重复消息 |  |  |
| 8 | 数据模型 | 状态取值、唯一索引、软删除是否支撑业务规则 1–7 |  |  |
| 9 | 时序正确性 | 报名/审批时序图与代码分支是否一致（含异常分支） |  |  |
| 10 | 可测试性 | 业务规则能否脱离 HTTP 测试；是否存在隐藏依赖 |  |  |
| 11 | 可维护性 | 变更（新策略/新渠道/名额扩容）预计影响范围是否可控 |  |  |
| 12 | 文档一致性 | 类图、用例图、SRS、README 的描述是否互相矛盾 |  |  |
